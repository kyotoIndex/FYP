5 Evaluation
5.1 Experimental Settings
5.1.1 Memory Capacity Heterogeneity. We define four memory ca-
pacity levels (Level 1-4) based on real-world NVIDIA GPUs. For FMs
with millions of parameters, we set the client memory capacities to
24 GB, 32 GB, 40 GB, and 48 GB for Level 1 through 4, respectively.
For FMs with billions of parameters, the corresponding memory
capacities are to 32 GB, 40 GB, 48 GB, and 80 GB. See Supplement
Section B.2 for detailed capacity settings on different models. We
assume that clients are distributed across these levels in a 4:3:2:1
ratio, from the lowest to the highest memory capacity, reflecting the
higher prevalence of low-memory clients in real-world scenarios.
5.1.2 Data Heterogeneity. We evaluate our approach on five dis-
tinct datasets while simulating varying levels of Non-IID settings,
including category heterogeneity, task heterogeneity, and domain
heterogeneity.
Figure 3: The average accuracy vs. average memory utiliza-

Category Heterogeneity. We use CIFAR-100 dataset [16] and
LEDGAR dataset from LexGLUE [4] to simulate the category het-
erogeneity settings by skewing the label distribution across clients.
For the pre-trained model, we use ViT-base [9] for visual tasks and
BERT-base [8] for language tasks.
Task Heterogeneity.We use Natural Instruction (NI) dataset [28]
and Dolly-15K [7] dataset that contain diverse natural language
tasks to evaluate our approach under task heterogeneity. We use a
Llama-like model Data-Juicer-1B [5] and the OPT-1.3B [34] as the
pre-trained models for these two datasets, respectively.
Domain Heterogeneity. We use a customized DomainNet
dataset [22] (referred to as DomainNet-121), which contains six
visual domains, to simulate the domain heterogeneity by assigning
data from only one domain to each client. For this dataset, we use
ViT-base [9] as the pre-trained model.
We provide the details of data settings in Supplement Section C.
5.1.3 Baselines. To evaluate the effectiveness of Fed-pilot, we im-
plement seven baselines:
Baseline-Exclusive Learning (EL) excludes clients that cannot
train all LoRA modules. Baseline-Memory Saver (MS) allocates the
last 𝑢 LoRA modules according to the capacity, prioritizing the
training of more modules. Baseline-Memory Hogger (MH) allocates
the first 𝑢 LoRA modules according to the capacity, emphasizing
the utilization of shallow-layer features. HETLoRA [6] is a rank-
based method designed to accommodate heterogeneous clients with
varying LoRA ranks. FLoRA [29] assigns lower ranks to resource-
constraint clients and shares stacked LoRA modules for updates.
FlexLoRA [3] improves aggregation in rank-based methods using
SVD. FedRA [24] randomly allocates a subset of LoRA modules for
clients with limited memory capacities to train at each round.
5.1.4 Implementation Details. We use PyTorch to implement our
framework. All experiments are carried out on a server with 8
× NVIDIA RTX A6000 GPUs. The total GPU hours for running
all the experiments are over 3,000 GPU hours. For the configura-
tion of models, hyper-parameters, and FL settings, please refer to
Supplement Section B for more details.
