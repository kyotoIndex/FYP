# 阶段 C1：受限训练到底节省了什么（资源核算）

日期：2026-10-18。状态：**纸面核算，没有新实验。** 上游：[路线图](roadmap_2026-10-18_amplified_restricted.md) 阶段 C1，[研究文档 §0.1、§7](research_two_directions_2026-10-17.md)。

脚本：[checks/c1_resource.py](checks/c1_resource.py)（`python3 docs/designs/checks/c1_resource.py`）。模型结构取自 Hugging Face 的 config.json（Qwen2.5-0.5B / 1.5B / 3B，2026-10-18 核实）；LLaMA-2-7B 用的是标准配置。

## 1. 核算口径

- LoRA 加在全部线性层上（q、k、v、o、gate、up、down），每个分量的参数量是 d_in + d_out。
- 弱端只训练 r 个分量，未训练的分量**折进冻结权重**（Fed-PLoRA 的 Select-N-Fold 做法），所以只有 r 个分量是可训练参数。amp 另外需要保存这 r 个分量的起点副本（FP32）。
- 训练状态：FP32 参数、梯度、Adam 的 m 和 v，每个可训练参数 16 字节。
- 主干：bf16 冻结权重。
- 激活：微批 4 × 序列 512，梯度检查点（每层保存输入，重算一层），加上 FP32 logits 和它的梯度。这部分是**粗估**，只用来看量级。
- 计算量（每个 token）：冻结主干约 4N（前向，加上对激活的反传），LoRA 训练分量约 6P，amp 起点项另加 2P_r。

## 3. 结论

1. **上传量的节省是确定的，而且最大**：严格等于 r/R（R = 64、r = 8 时为 1/8）。
2. **训练状态的节省也严格等于 r/R**，但它只占峰值的一部分：R = 64 时峰值显存节省 **10–14%**（0.4–2 GiB），R = 16 时只有约 3%。
3. **计算量几乎不变**（≤ 8%）：反传的主要开销是穿过冻结主干，与 rank 无关。
4. 因此，"弱端训练不起完整 rank，必须受限训练"只在显存非常紧张、R 较大时才成立（例如显存刚好差 1–2 GiB 的设备）。**不能把它作为主要卖点。**

## 4. 建议的论文卖点

> 在异构 rank 联邦 LoRA 中，弱端只训练并上传 r 个分量：上传量和 LoRA 训练状态都降为 r/R（R = 64 时峰值显存约少 10–14%），精度与所有客户端完整训练 rank R 相同。

需要如实说明的几点：
- 与 vref（弱端完整训练、只上传 r 个分量）相比，精度相同，amp 额外节省的只是训练状态（峰值显存 10–14%）和少量计算；
- 与 FLASC 式（完整训练 + 稀疏上传）相比，amp 训练得更少，精度反而高 0.79pp（[§8](research_two_directions_2026-10-17.md)）；
- 方法的主要价值在于：当系统**已经**选择或被迫只训练部分分量时（这是 HetLoRA、FlexLoRA、Fed-PLoRA、FSLoRA 等已有工作的共同设定），它消除了这种做法的精度代价。这是"修复一个常见设定中的缺陷"，而不是"让原本训练不了的设备能训练"。

## 5. 对阶段 C2 的影响

1. **设定**：用 R = 64、r = 8（α = 8），这时资源差异最明显。α = 8 在 RoBERTa 上已经验证过：r = 1 的稳健性实验中 α = 8，追回比例为 1.01。
2. **实现必须真正省显存**：当前代码把未训练分量保留为参数，只把梯度清零，AdamW 仍然为它们分配状态，所以**测不出显存节省**。C2 的代码要把未训练分量折进冻结权重，只把 r 个分量作为参数，这样才能实测峰值显存。
3. **要测的量**：弱端训练 r 与训练 R 时的峰值显存和每步时间，用来检验上表的估计。
4. **预测**（C2 事先写定）：
   - 解码器模型没有从零训练的分类头，压力全部落在 LoRA 分量上（类似 D3 中冻结头部时 2.3–2.5 倍的过冲），所以 L2 的差距应当仍然存在；
   - amp 应当追平 vref；
   - 峰值显存的节省落在上表的 10–14% 附近。
